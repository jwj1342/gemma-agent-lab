## Findings

### 1. [P1] Preserve explicit content beside native tool calls

Location: `src/sft_data.py:115-123`, called at line 138 and discarded at line 155.

`assistant_reasoning()` only reads `reasoning` and `reasoning_content`.
For an assistant message with native `tool_calls` and explicit reasoning in
`content`, enabling `preserve_reasoning` produces the same actions-only output
as disabling it. Conversion replaces content with an empty string and never
copies this text into the reasoning field. Thus the proposed training fix does
not address the row shape identified by jwj1342 in the existing review.

I independently reproduced the behavior with the synthetic row below. I did not
inspect the owner's private parquet shard or independently verify the reported
21,424-message statistics or adapter scores. This is confirmation of the owner's
existing blocker, not a newly discovered dataset finding.

Suggested fix: under the opt-in policy, support `text_content(content)` on native
tool-call messages, define precedence/conflict handling with explicit reasoning
fields, and add a representative row-shape regression test. Preserve the default
actions-only behavior. XML action parsing can remain a separately scoped change;
it is an existing limitation rather than a new regression from this PR.

```python
import json
from src.sft_data import convert_trajectory

row = {"resolved": True, "messages": json.dumps([
    {"role": "user", "content": "Fix the bug."},
    {"role": "assistant",
     "content": "The list is shared; copy it before mutation.",
     "tool_calls": [{"id": "c1", "function": {
         "name": "bash", "arguments": {"command": "git diff"}}}]},
    {"role": "tool", "tool_call_id": "c1", "content": "Observed diff."},
])}
assert convert_trajectory(row, preserve_reasoning=True) == convert_trajectory(
    row, preserve_reasoning=False)
```

The assertion currently passes: the opt-in flag has no effect on this row.

### 2. [P2] Do not turn partial diff parsing into complete file membership

Location: `src/failure_mechanisms.py:165-170`, with header parsing at lines 112-129.

The new guard returns unknown for a standalone headerless rename, but accepts
partial results when the same patch also contains a normal textual hunk.
`patch_paths()` only collects `---` / `+++` paths. Therefore a patch modifying
`notes.txt` and purely renaming `pkg/old.py` to `pkg/new.py` returns only
`['notes.txt']`. If `pkg/old.py` is a reference file, `audit()` reports
`final_patch_reference=False` despite the rename affecting that file. With a
source exposure it can also report `read_no_reference_patch=True` incorrectly.

I reproduced this with a real Git repository: commit the two synthetic files,
rename the Python file without changing its bytes, modify the text file, stage
both changes and obtain `git diff --cached --find-renames`. The diff contains
the valid mixed structure shown below. A standalone rename returns `None`;
adding an unrelated recognized text hunk incorrectly changes unknown into a
definite but incomplete membership result.

```python
from src.failure_mechanisms import audit, prediction_paths

text = ("diff --git a/notes.txt b/notes.txt\n"
        "--- a/notes.txt\n+++ b/notes.txt\n"
        "@@ -1 +1 @@\n-old\n+new\n")
rename = ("diff --git a/pkg/old.py b/pkg/new.py\n"
          "similarity index 100%\n"
          "rename from pkg/old.py\nrename to pkg/new.py\n")
assert prediction_paths({"agent_patch": rename}) is None
assert prediction_paths({"agent_patch": text + rename}) == ["notes.txt"]
result = audit({"steps": []}, {"agent_patch": text + rename},
               {"pkg/old.py": [{"old_start": 1, "old_len": 1}]})
assert result["final_patch_reference"] is False
```

These assertions reproduce the defect, not the desired behavior. Suggested fix:
track parsing completeness per Git file section and return unknown if any section
is unsupported, or implement reliable rename/binary/mode-change path extraction.
Add mixed-section regressions, including trace-present and trace-missing paths.
No evidence was established that the published r4/r5 counts contain this case.
