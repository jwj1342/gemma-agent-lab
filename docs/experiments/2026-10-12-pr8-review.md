## 3. Review area 1 — native chat-template boundaries and handoff token 50

### 3.1 What the code enforces (read from the reviewed revision)

`src/sft_data.py::encode_example` builds a prefix/completion pair from the same template call and
then refuses to continue unless all of the following hold:

- the rendered whole string starts with the rendered prefix string;
- the tokenized whole starts with the tokenized prefix (`whole_ids[:len(prefix_ids)] == prefix_ids`),
  which is what makes the prompt/target loss boundary real rather than assumed;
- a tool-call target ends with `<|tool_response>`;
- the target is non-empty and shorter than half the maximum length;
- oversized examples are shortened by deleting whole earlier action/observation pairs, so a
  half-turn is never left behind.

`scripts/encode_sft_dataset.py` adds the boundary contract around it:

- the stop token is resolved from the tokenizer and required to be in `generation_config.json`'s
  `eos_token_id` **before** any encoding work, so a template/tokenizer mismatch fails immediately
  rather than after a GPU allocation;
- for every tool-target sample the last input token **and** the last label token must equal the stop
  id;
- for every terminal sample the target must end with `<turn|>` followed by a newline;
- `protocol-examples.json` records a representative target prefix/suffix and final token id per split
  and source, which is the artifact to inspect for "native protocol examples".

The manifest's `encoding_protocol` records `tool_handoff_stop_token: <|tool_response>`,
`tool_handoff_stop_id: 50` and `tool_handoff_is_supervised: true`, consistent with the code.

### 3.2 Findings

1. **The thinking channel is always supervised (highest-value question).**
   `apply_chat_template(..., enable_thinking=True)` is hardcoded in `encode_example` for every
   example, including tool-call targets. The document records that the short serving probes ran with
   thinking **disabled** for both models, while autonomous evaluation kept the baseline thinking
   configuration. So training always includes the thinking channel, and the short-probe comparison
   was run in a configuration that training never used. The restricted comparison cannot isolate
   this, because it changes sampling, loss weighting and prompt context together. This deserves one
   sentence in the limitations list, which does not currently mention it, and it is the first thing I
   would confirm against the harness before more training.
2. **A dropped terminal action is silent (small, fixable).**
   In `convert_trajectory`, an assistant turn with no tool calls is only kept when it is the last
   message, the previous message is a tool observation **named** `submit_patch`, and its text is
   non-empty; otherwise it hits a bare `continue`. Any upstream trajectory whose submission
   observation carries a different name loses its supervised terminal answer with no counter and no
   error. This project has already been bitten by silent drops, so a counter or a strict failure is
   worth more than the current silent branch.
3. **Validation evidence is truncated evidence (small, documented choice).**
   Observation truncation to `excerpt_chars` (12,000 for the compact recipe) is applied before the
   template checks, and it applies to validation samples as well — only the training terminal system
   prompt is replaced, and the held-out encoded population is deliberately byte-identical across
   runs. Validation NLL is therefore measured on middle-truncated observations. That is a defensible
   fixed instrument, but the truncation marker inside the context is a training-time artifact that
   does not exist at serving time.
4. **Verified positive.** The token-prefix assertion is the strongest part of this area: a template
   change that shifts the loss boundary cannot pass silently, and the stop-token presence check runs
   before any model work.

## 4. Review area 2 — the save/restart contract

### 4.1 What it is

`scripts/train_swe_lora.py` builds a `contract` from the config, the versions of
`torch`/`transformers`/`peft`/`compressed-tensors`/`accelerate`, the encoded data-manifest hash, the
world size, the SHA256 of the base `config.json` and `model.safetensors`, and the SHA256 of the
trainer and scheduler sources. It is written once to `run-manifest.json`; on resume, any difference
raises `Resume contract changed`. Checkpoints hold `training_state.pt` (step, optimizer state,
per-rank Python/torch/CUDA RNG, best SWE NLL, samples and tokens) plus `validation.json`, and
`latest.json` / `best.json` name the retained checkpoints.

The recorded recovery receipt is `restored_step: 8`, `optimizer_and_rng_restored: true`,
`contract_matches: true`, followed by update 9 with a finite loss and gradient norm 17.06 — a real
restart, not a re-initialisation.

### 4.2 Findings

1. **Verified positive.** The contract pins exactly the three things that silently invalidate a
   resume: different data, different dependency versions, different world size. Most training code
   checks none of them.
2. **Single-file checkpoint assumption (portability risk for the L4 path).**
   `base_weights_sha256` digests `args.base / 'model.safetensors'`. A sharded base
   (`model-00001-of-000NN.safetensors`) has no `model.safetensors`, so the trainer raises before the
   first step. This should either hash every shard or fail with a message that names the layout; it
   matters for the L4 work because any unquantized fallback base may be sharded.
3. **Retention window (minor).** After `rename`, older `checkpoint-*` directories not in
   `{latest, best}` are deleted, while `best.json` is read back on the next save. An interruption
   between the two leaves `best.json` pointing at a deleted directory. The recorded run did not hit
   it, and `run-manifest.json` would make the mismatch visible.
4. **Trust note.** `training_state.pt` is loaded with `weights_only=False`. The module docstring
   already forbids third-party pickles; this is the one place a resume trusts a pickle, and it is our
   own artifact. Acceptable, worth knowing.
5. **World size is pinned by design.** Moving the same run from one H100 to four L4s is refused by
   the contract, which is correct behaviour and is why the L4 feasibility work starts a new adapter
   from the frozen base instead of resuming the H100 run.

## 5. Review area 3 — the early agent gates

### 5.1 What runs

`scripts/slurm_preflight_swe_lora_light.sh`, per registered task, in order:
`prepare_eval_run.py` (freezes agent, task and budget hashes and writes the runner) → `compile` →
`verify --patch-source empty` → `verify --patch-source gold` →
`summarize_eval_smoke.py --controls-only` → `infer` → `verify --patch-source agent` →
`summarize_eval_smoke.py`. The launcher runs under `set -eo pipefail`.

### 5.2 Findings

1. **Verified positive — the gate actually blocks inference.**
   `scripts/summarize_eval_smoke.py` raises `SystemExit` when any check in its result is false, and
   under `set -e` that stops the job before the `infer` line. So a task whose empty or gold control is
   invalid cannot consume inference time. This is the correction the document describes after job
   `1072977` failed when `inline_snapshot` was missing and the single-task runner had skipped the
   isolated offline dependency setup.
2. **Verified positive — execution and resolution are reported separately.**
   The summary separates `controls_valid`, `pipeline_executed` and `agent_resolved`, and the fixed
   comparison keeps `resolved`, `clean` and `resolved and clean` as distinct columns. The
   `requests_7502` case — a patch that passes grading while the agent exhausted its turns — is
   recorded as resolved-but-not-clean rather than being silently counted as a success. That is the
   distinction the task asks for.
3. **Scope limitation.** The loop covers `fastapi_14455` and `requests_7502`; `rich_3454` is driven by
   the parent launcher, and any failure stops the loop. So this file is a per-task gate, not a
   three-task gate: it cannot by itself demonstrate that all three registered probes passed, which is
   why the three outcomes in the evidence come from jobs `1072977`, `1073256`, `1073459` and
   `1073600`. The document says so, and the manifest keeps every outcome including the failures.
4. **Unchanged by this work.** The L4 feasibility check uses a different gate on purpose (adapter
   validity, then official-runtime honouring of the adapter). A training-feasibility result must not
   be readable as an agent-performance result, and the agent gates stay as they are for the
   evaluation path.

## 6. Cross-cutting finding that shapes the L4 work

The trainer on this branch cannot run on Kaggle unchanged, and not for a configuration reason:

- it raises without `SLURM_JOB_ID`;
- it loads **full BF16 replicas** (`CompressedTensorsConfig(dequantize=True)`, no sharding) and wraps
  them in DDP, with a recorded peak of 67.38 GiB, against 22.5 GiB usable per L4;
- its Slurm launchers take Trillium paths, modules and virtual environments.

That is a Trillium-only entry point, which is exactly why issue #13 asks for a separate L4 path
rather than a parameter change. The L4 instrument and its compatibility analysis are in
`docs/experiments/2026-10-12-l4-training-feasibility.md`.

## 7. Recommendation

**From a reproducibility standpoint the recorded evidence is in good shape, and the save/restart
contract is stronger than the summary suggests.** The 5-for-5 source hash verification and the
consistency of coverage, cost and outcome figures are what I would expect from a merge-ready research
handoff. Two small changes are worth making before merge, both cheap:

1. count or fail when a terminal assistant turn is dropped because the preceding observation is not
   named `submit_patch`;
2. hash every base weight shard (or fail with a clear message naming the layout), instead of assuming
   `model.safetensors`.

Not merge-blocking, but it should be explicit: `enable_thinking=True` is applied to all training
targets including tool calls, while the short serving probes disabled thinking. One sentence in the
limitations list closes that gap.

The adapter itself stays unpromoted and unuploaded, and the evidence supports that: patch resolution
3/11 versus 2/11, clean nonempty completion 4/11 versus 8/11, both resolved and clean 2/11 each, and
the registered three-task gate failed. At n=11 with a worse completion rate and longer inference,
"one extra solved task" is not a gain.
