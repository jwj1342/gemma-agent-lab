# Complete-epoch SWE LoRA: execution record

Status on October 10: the first four-GPU job completed eight updates and saved a
checkpoint, then failed during fresh-process recovery. The failure was a PEFT /
Transformers compatibility error specific to loading after distributed process-group
initialization. The single-GPU recovery preflight had not exercised that path.
The loading order is corrected. The new four-GPU recovery gate passed: a fresh
process restored step 8 and completed step 9, validation and another checkpoint.
Full continuation passed its first 100-update validation and checkpoint, then
encountered a CUDA OOM while attempting step 137. A recovery attempt now restricts
each worker to its assigned GPU and replays from checkpoint 100. Training completion and
submission remain pending. This report does not claim convergence or a repair-rate improvement.

## Question and comparison

Can standard LoRA improve the required Gemma model's repair actions, graph-tool
arguments and task termination? Compare the unchanged baseline agent with the same
agent using the trained adapter on its root model. Keep generation settings, tools,
per-task budgets, public tasks and the version 29 evaluation runtime fixed.

The corpus mixes upstream successful SWE-smith trajectories with locally executed
graph and terminal component exercises. This first combined candidate cannot
identify the graph component's individual contribution; that needs a later ablation.

### Quantized serving preflight

Job `1063979` loaded the two-update probe checkpoint in the official version 29
W4A16 server and completed all twelve held-out action/termination requests. The
all-projection adapter can be loaded. This is compatibility evidence only.

Its initial probability-effect result is **invalidated**: Transformers 5 defaults
`apply_chat_template` to a mapping, which the client treated as an iterable of
mapping keys instead of the intended token IDs. The identical distributions across
different contexts exposed the problem. Training encoding is unaffected: it renders
text with `tokenize=False` and explicitly encodes that text. Chat-completion action
requests also use their actual message lists.

The corrected probe explicitly requires a flat token-ID list, checks the server's
consumed-token count, and records each prompt hash. It compares the trained adapter
against a second adapter with every LoRA B matrix zeroed, including a repeated-zero
control. This separates trained-weight effects from numerical changes caused by
switching to the adapter execution path. The first probability delta must not be
cited as evidence that learned weights work.

Job `1063997` then exposed a second measurement issue: cached and uncached
prefills produced different low-probability logits even for repeated zero-update
requests. That run correctly failed the effect gate. The final probe disables
prefix caching for this diagnostic server only, so every request uses a full
prefill. This does not change the frozen repair-evaluation protocol.

Job `1064011`, validation source `e13025f`, **passed** in 4m23s. All 63 repository
tests passed in its allocation. The server consumed the intended 1,067 / 648 / 754
token prompts, with distinct recorded hashes. Repeated base and zero-update
distributions matched exactly; trained-versus-zero top-token log probabilities
differed on all three probes (maximum differences approximately 0.125). All twelve
action/termination request pairs completed. This establishes adapter loading and a
measurable weight effect for the two-update checkpoint, not task improvement or
completed training. The full trained export must pass the same checks again.

## Four-GPU recovery correction

In PEFT `0.19.1`, an initialized process group triggers the legacy tensor-parallel
adapter-loading helper even for DDP replicas. That helper imports
`EmbeddingParallel`, which is absent from Transformers `5.18`. The original job
therefore failed before optimizer/RNG restoration, despite a valid saved adapter.
The eight recorded updates covered 64 actions and 9,059 assistant tokens; SWE
validation NLL was 0.621132, versus 0.621230 initially. These early measurements
do not establish convergence.

The trainer now loads each complete model and adapter on its explicit local device
before initializing NCCL and wrapping the model in DDP. No installed package or
official evaluation code is patched. Resume contracts also include package versions.
The corrected run uses a fresh output directory and the same immutable encoded
corpus; it does not rewrite the failed run's source contract or reuse an incompatible
manifest. A four-rank save/restart/update check is required before full continuation.

The upstream helper's current implementation first checks for actual TP modules
before importing legacy TP classes; see the
[PEFT source](https://github.com/huggingface/peft/blob/main/src/peft/utils/save_and_load.py).
Our correction keeps the installed Alliance environment and the existing DDP design.

The corrected artifact root is `runs/20261010-swe-lora-v1-ddp/`, with frozen source
`7ab3bd4` under `inputs/training/`. Job `1067669` passed 63 repository tests and
the four-rank recovery gate in 5m48s. The gate records restored optimizer/RNG state,
matching source/data/dependency contracts, and step 9 with 72 cumulative actions.
The failed original directory is retained unchanged apart from its status receipt.

Full continuation `1067671` resumes the validated checkpoint to complete 4,248
updates / two epochs. Validation `1067672` depends on its success and reuses the
already validated version 29 source `e13025f` for adapter effects, controlled smoke,
and the matched fast cohort. `recovery-gate.json` preserves the preflight result
before later resumes update `train/resume-check.json`. The run's `job-receipt.json`
links these jobs and the original corpus.

## Memory failure and isolated worker recovery

Job `1067671` failed during backward for step 137 after recording 136 completed
updates. Its latest complete recovery state is checkpoint 100; dependent validation
`1067672` was cancelled. The failed allocation is terminal, so it is safe to start
one replacement attempt. Earlier finite losses and a 69.32 GiB Torch peak did not
establish enough driver-level memory headroom for every batch.

The OOM report showed the other three training worker PIDs each occupying about
992 MiB on GPU 0, alongside the main worker's allocations. The new launcher sets
each worker's `CUDA_VISIBLE_DEVICES` before executing a fresh Python interpreter,
then uses process-local CUDA device zero. Global ranks and world size are preserved.
This prevents workers from initializing CUDA on another worker's allocated GPU.
It follows the per-process device isolation described in
[PyTorch DDP](https://docs.pytorch.org/docs/stable/generated/torch.nn.parallel.DistributedDataParallel.html).

The core trainer and schedule files are byte-identical to the checkpoint's source
contract. No context length, examples, batch size, model, optimizer, dependency or
source-hash checks are relaxed. Frozen launcher source is `e1cb5ce`, under
`inputs/training-isolated/`. Recovery job `1067805` is registered to replay steps
101–150 and record actual worker/GPU memory placement. Full continuation `1067810`
and validation `1067811` depend on success. The GPU-memory fix remains unverified
until the recovery gate passes the previously failing batch.

`isolated-recovery.json` records the source checks and prior metric-log boundary.
Uncheckpointed metrics 101–136 from the failed attempt remain in the append-only
log, followed by replayed steps from the replacement attempt. Do not sum both
attempts as unique training coverage. Final coverage is measured by the restored
training state's counters and `completed.json`.
